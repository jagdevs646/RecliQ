## Recommended Approach
Approach A. It puts the payroll job in front of real people within days, on infrastructure that already runs, and reuses the GST preset detection, saved setups, one-click re-run and guest deletion.

Scope of the build:
1. A payroll preset: named inputs "Payroll register" and "Bank payout file"; guessed key and amount mapping that the user confirms (key rules below); three outcome groups (paid twice or not in register; in register but not paid; wrong amount or account), each row with a one-line reason.
2. A payroll landing view that leads with that outcome, a "Use a sample file" path with synthetic data, and the full six-step setup still reachable for other reconciliations.
3. "Save as my payroll check" producing a saved setup for the next cycle's one-click re-run.
4. A plain "Where your files go" page, worded from the data inventory below and checked against the real deployment before it is published.
5. An "Ask for the desktop version" link whose requests are counted (the Approach B trigger).
6. Manual invoicing for the first customers; no billing code.

### Payroll matching rules (decided)
- **Key.** The key is an identifier present in both files: employee ID when the bank payout file carries it (often in the narration or reference column), otherwise the employee name. Bank account number is never the key; it is compared as a field, so "wrong account" is a real outcome. When the key is the employee name, every pairing that is not an exact name match goes to review, and the result says that names were used.
- **Exactness.** Exact matching on the key; no fuzzy or reference-variant matching of employee IDs or account numbers (the reference level is "exact"). Amount tolerance defaults to zero; the user may set one explicitly, and the result states it. Any proposed pair that is not exact goes to review, never to matched.
- **IDs inside narration text.** Bank payout files usually carry the employee ID inside free text (for example "SAL NOV EMP0123 RAHUL"), and the engine matches whole cell values. The preset therefore adds a preparation step that extracts the ID from the narration with a pattern the user confirms on their own file (for example `EMP` followed by digits). This extraction step is new work; no current preparation step does it. A run uses one key: the engine joins on a single key definition per run. If the pattern finds an ID in the bank file, the run is keyed on employee ID, and bank rows with no ID found go to a separate review group, "no employee ID in narration", showing name, amount and account. The run is keyed on employee name only when the bank file carries no IDs at all, and the result says which key was used.
- **Duplicates in the register.** The register may hold several lines per employee (salary plus reimbursement or arrears). Register lines that share an employee ID are summed into one expected payout per employee, as the engine's consolidation does today, and the result shows the number of register lines behind each total.
- **Duplicates in the bank payout file.** Consolidation is turned off for the bank side only (a new per-preset, per-side switch). A key that appears more than once in the bank file is reported row by row. When the key is the employee ID, repeated rows go to "paid twice", unless they sum exactly to the register amount (or within the tolerance the user set), in which case they are a split payment for review.
- **Repeated names.** When the key is the employee name, a name that appears more than once in either file is never reported as "paid twice"; it goes to review as "same name, more than one person or payment", with amount and account shown, because two employees can share a name.
- **Outcome groups.** Group 1's reason names which case each row is: "paid twice" (recover a payment) or "not in register" (stop or investigate the payment).

### Accounts, saving and retention (decided)
- A one-off check works for guests, and guest files, results and saved setups are deleted after 24 hours, as today. The result page says so next to "Save as my payroll check".
- Saving a payroll check needs an account. "Save" asks the guest to register at that point, and the guest's run moves into the new account through the existing explicit guest-workspace import. If registration waits on email verification or administrator approval, the page says so and the run stays available until the guest deletion time.
- Registered accounts: everything a payroll-preset run stores that holds payroll data is deleted 14 days after the run, or immediately when the user deletes the run. That covers uploaded files, generated reports, report email deliveries and their access links, review decisions and outcomes. The audit log is append-only and cannot be deleted from, so audit events for payroll-preset runs must record only identifiers and counts (run ID, file names, row counts), never employee names, IDs, accounts or amounts; a test checks this. The saved check keeps only column mapping and rules, no payroll data. Registered accounts already have a retention policy (report_retention_days, 365 days by default, set by the administrator and applied by prune_old_jobs); payroll-preset runs use the shorter of 14 days and that policy, through the same pruning path, with its own setting and test.
- Learning is off for the payroll preset: no name aliases, learned decisions or exception patterns are created from payroll runs, so employee names and IDs are not kept in learning stores. Resolution rules the user writes by hand are kept, because they are the user's own configuration.

### How success is measured
- A payroll check counts as "run on their own files" when it is a finished payroll-preset run that did not use the sample file. Sample runs are marked as such and excluded.
- Re-runs are counted from the existing `template.run` audit events on saved payroll checks, per account. "Without help" is the founder's own log of support given, kept per user.
- A "completed web check" is a finished non-sample payroll run; desktop requests are compared against that count.
- The founder reads these counts per account in the admin console's product insights; any count the console lacks is added there.

Data flow, payroll run: happy — two files, preset detected, IDs extracted, four groups. Nil — a file missing: existing upload validation rejects the run. Empty — register with zero rows: must say "the register has no payment lines" instead of an all-"not in register" result (finding A-1). Error — engine failure: existing job failure path shows the error; partial files are deleted by the normal job-failure path.
Data flow, sweep: happy — deletes expired runs and clears pending rows. Nil — nothing expired: no-op, records the sweep time. Empty — pending table empty: no-op. Error — storage down: rows go to pending; database down: the endpoint returns 503 and the workflow retries once.
State machine, pending deletion: `recorded → retried(n) → deleted`; never deleted twice (claimed under lock); a row cannot return to "recorded" after deletion.
Coupling: the `delete_file` contract change touches every storage caller and RecliQ Desktop's vendored copy (A-2). Justified: silent deletion failure is the defect.
Scaling: payroll files are hundreds to tens of thousands of rows; the engine runs 100,000 rows in about 12 s [measured: scripts/perf/bench.py, 2026-11-04]. The sweep first breaks at 10x accounts only if it scans all jobs without an index (see Section 7).
Single points of failure: the sweep depends on either the process being up or the GitHub workflow; both failing is visible through the last-sweep time.
Security architecture: one new endpoint (admin sweep, token-auth); data access stays workspace-scoped through existing routes.
Production failures: (1) GitHub schedule paused → last-sweep alarm; (2) Azure 5xx on delete → pending row; (3) cold start beyond timeout → retry once.
Rollback: turn the payroll preset off through the existing feature policy; migrations are additive; revert the deploy in Render (minutes).
